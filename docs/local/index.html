01. Como as peças se conectam

O domínio é o endereço. O DNS informa onde ele está hospedado. A hospedagem executa a aplicação; o HTTPS protege a conexão do navegador.

Navegador→DNS + HTTPS→Next.js→Spring Boot→PostgreSQL / Redis

O repositório contém Next.js 16, Java 21, Spring Boot, PostgreSQL 16 e Redis 7, reunidos pelo Docker Compose. A estrutura permite começar com uma VPS e separar serviços quando a medição justificar.

A landing page usa o endereço principal. O app tem endereço próprio. O blog é uma proposta de hospedagem: a escolha de CMS e o modo de publicação ainda precisam ser definidos. Esta página de documentação funciona separadamente, inclusive sem internet; apenas as fontes externas precisam de conexão.

Diferença encontrada nos arquivosO README e a baseline pedem Node.js 24 para os testes locais; frontend/Dockerfile ainda usa node:20-alpine. Alinhar o runtime e validar o build antes de produzir uma imagem para publicação. Nenhum Dockerfile foi alterado por este guia.

São hipóteses de engenharia, não capacidade comprovada. Ainda não há teste de carga que permita prometer uma quantidade de barbearias. Builds de Java e Next.js também disputam recursos; considere gerar as imagens fora da VPS.

Meça memória, CPU, disco, erros e tempo de resposta. Amplie ou separe componentes quando houver pressão sustentada, lentidão ou interferência entre o blog e os agendamentos. Um servidor único concentra as falhas: backup não substitui alta disponibilidade.

Usar o KVM 2 como referência de orçamento em reais, considerando principalmente a renovação. A oferta inclui backup semanal, mas a VPS continua autogerenciada. Hetzner é uma alternativa econômica se houver estoque e a latência for adequada. Não há fornecedor contratado.

Frontend separado

A Vercel Pro tinha referência de US$ 20/mês em 23/09/2026, mais eventuais cobranças por uso e equipe. Revalidar no catálogo. O Hobby restringe uso a projetos pessoais não comerciais; não adotá-lo como orçamento do SaaS.

Landing page e blog podem usar hospedagem estática se sua implementação permitir. CMS, SSR, formulários e integrações podem exigir execução no servidor e custos próprios. O frontend autenticado atual não deve ser tratado como simples exportação estática.

Configuração planejada

  1. Registrar o domínio e adicionar a zona na Cloudflare. No registrador, usar exatamente os nameservers fornecidos.
  2. Criar os registros da tabela de endereços. A aponta para IPv4; AAAA somente com IPv6 funcional; CNAME aponta para nome de host.
  3. Configurar no proxy os destinos de landing page, app e blog. DNS não faz redirecionamento HTTP nem escolhe portas.
  4. Emitir certificados para cada nome público, usando por exemplo Let's Encrypt, e habilitar renovação automática. Se usar proxy Cloudflare, manter HTTPS válido também até a origem, em modo Full (strict).
  5. Configurar o redirecionamento de www para o domínio principal no servidor. Não criar DNS para as docs.
  6. Revisar NEXTAUTH_URL, callbacks OAuth e escopo dos cookies para o host do app. CORS só com as origens necessárias se houver API separada.

O Compose usa proxy interno entre Next.js e backend. Preservar esse desenho pode dispensar um endereço público de API. Não apontar o navegador para o hostname Docker backend; ele só resolve dentro da rede de containers.

Quanto sai na contratação?

O desembolso depende do período promocional escolhido: R$ 43,99 × número de meses + domínio anual. Por exemplo, se a oferta for válida por 24 meses, a VPS seria R$ 1.055,76, mais R$ 40 de domínio no primeiro ano: R$ 1.095,76. É uma simulação, não uma confirmação do checkout. O domínio precisaria de nova renovação no segundo ano.

A renovação anunciada da VPS, a R$ 77,99 por 24 meses, equivale a R$ 1.871,76 por ciclo, antes dos demais itens. Confira a oferta e o total antes de contratar.

Cenário B · frontend separado

Com a mesma VPS e Vercel Pro de US$ 20 (≈ R$ 110), a base ilustrativa fica em R$ 157,32/mês promocional ou R$ 191,32/mês na renovação; equivalentes anuais de R$ 1.887,88 e R$ 2.295,88. Soma o plano de frontend uma única vez; uso excedente e outras licenças ficam fora.

Hospedagem estática gratuita para landing page/blog só entra no orçamento após confirmar compatibilidade e limites. Se houver CMS ou hospedagem adicional, somar a cotação específica. O desembolso inicial do cenário B é o contrato da VPS + domínio + primeira cobrança da Vercel + eventual CMS.

Reserva sugerida: R$ 100–150 por mês no cenário AEstimativa para planejamento, com margem sobre o custo base. Não é cotação de operação gerenciada nem garante cobertura de todos os serviços. O cenário B exige orçamento maior.

08. Instalação e preparação

Os comandos abaixo foram confrontados com os nomes de serviços e arquivos do repositório. Não foram executados contra uma VPS nem constituem deploy validado. A documentação local não executa comandos por você.

Executar o ambiente de desenvolvimento

Instale Docker com Compose. No PowerShell, a partir da raiz, crie o arquivo de configuração somente se ainda não existir:

if (!(Test-Path frontend/.env.local)) {
  Copy-Item frontend/.env.local.example frontend/.env.local
}
# Preencha NEXTAUTH_SECRET antes de iniciar.
docker compose up --build -d
docker compose ps

Use http://localhost:3000 para o painel e http://localhost:8080/swagger-ui/index.html para a API local. Integrações opcionais são descritas no arquivo de exemplo; mantenha segredos apenas nos arquivos de ambiente apropriados.

Antes de qualquer publicação

  1. Preparar VPS Linux e acesso SSH com chave, seguindo a instalação oficial de Docker para o sistema escolhido.
  2. Alinhar o runtime Node do Dockerfile e validar as imagens e migrações em homologação.
  3. Criar configuração de produção separada. O Compose atual contém credenciais de desenvolvimento e publica PostgreSQL, Redis e backend no host.
  4. Substituir segredos de desenvolvimento e remover exposição pública do banco e Redis. Publicar somente os serviços necessários através do proxy; restringir SSH.
  5. Configurar volumes, limites de recursos, política de reinício, prontidão e logs. O depends_on do frontend não garante que a API esteja pronta.
  6. Configurar os hosts públicos e HTTPS conforme a seção anterior. Validar login, agendamento e autorização, incluindo isolamento entre contas.
  7. Preparar backup externo e restauração testada antes de aceitar dados reais. Registrar release e plano de reversão.

Não usar o comando de desenvolvimento como receita de produção. A configuração final depende de proxy, domínio, provedor e implantação ainda não definidos.

09. Backup, atualização e diagnóstico

Backup que permite recuperar

Defina frequência e retenção conforme a perda de dados aceitável. Uma referência inicial é backup diário do PostgreSQL, cópia externa criptografada e teste periódico de restauração em ambiente isolado. Armazene também arquivos enviados pelos usuários, se houver, e configurações necessárias à recuperação.

Snapshots semanais da VPS não substituem uma estratégia consistente de banco. Confirme se Redis guarda apenas dados recriáveis antes de excluí-lo do plano. Registre a data do último backup bem-sucedido e o tempo de recuperação medido.

Atualizações

Gere e teste imagens de uma release identificada, faça backup, aplique em homologação e só então programe a publicação. Migrações já aplicadas não devem ser reescritas; o rollback da aplicação pode exigir compatibilidade com o banco atualizado.

11. CRM e WhatsApp oficial

Decisão de produto · 25/09/2026 · requisito para implementação, ainda não implementado.

Descrição da tarefa

Refatorar CRM & WhatsApp conforme o SVG anexado à tarefa, mantendo o design system atual. Integrar o LineUp diretamente à API oficial do WhatsApp Business (Meta), para seguir o fluxo suportado de mensagens, modelos aprovados e notificações de entrega, evitando a dependência de sessões não oficiais do WhatsApp Web.

Criar uma área de Configurações → Integrações → WhatsApp para o administrador de cada barbearia conectar sua própria conta e número, cadastrar ou autorizar as credenciais necessárias, testar a conexão e consultar seu status. As credenciais devem ficar protegidas no backend e isoladas por barbearia. Informar que o consumo de mensagens pode gerar cobrança da Meta.

Escopo e critérios de aceite

  • Manter o SVG anexado no Trello como referência visual. O anexo não foi inspecionado nesta documentação.
  • Adotar conexão oficial direta. A recomendação anterior de Evolution com Baileys é substituída por esta decisão. Evolution com Cloud API também usa o canal oficial, mas não é necessária no escopo definido e não elimina tarifas da Meta.
  • Permitir conexão, teste, atualização e desconexão apenas ao administrador autorizado da barbearia. Mostrar estados: não configurado, conectado e erro, com orientação útil.
  • Definir o fluxo de conexão: autorização guiada da Meta ou configuração de WABA ID, Phone Number ID e token com permissões apropriadas. Não solicitar a senha pessoal do Facebook ou WhatsApp.
  • Armazenar tokens de forma cifrada no backend, mascarar na interface, excluir de logs e não devolvê-los em respostas de consulta. Validar que conta e número pertencem à integração autorizada.
  • Configurar e validar webhooks, roteando mensagens e status para a barbearia correta. Testar que uma barbearia não acessa credenciais ou eventos de outra.
  • Usar modelos aprovados quando exigidos; respeitar consentimento, descadastro e janela de atendimento. Não prometer ausência de bloqueios: as políticas da Meta continuam aplicáveis.
  • Apresentar consumo e responsabilidade pelos custos. Não implementar envios reais ou cobrança sem concluir a configuração e as validações.
